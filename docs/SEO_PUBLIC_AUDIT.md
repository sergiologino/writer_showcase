# SEO публичного блога — аудит этапа 5

Дата: 18 октября 2026.

## Текущее состояние

- URL сохранены: `/blog/:workspaceSlug` и `/blog/:workspaceSlug/p/:postSlug`. Публичный API отдаёт только материалы со статусом `PUBLISHED` и видимостью `PUBLIC`; страница статьи использует тот же slug.
- Backend отдаёт `/robots.txt` с запретом `/app/`, `/auth/`, `/login`, `/register`; `/sitemap.xml` перечисляет главную, блоги и опубликованные публичные статьи. Nginx проксирует оба файла на backend.
- `Seo` обновляет title, description, canonical, Open Graph, Twitter Card и robots после рендера React. Для статьи значения берутся из ответа публичного API. Для не найденной статьи выставляется `noindex`. Лендинг сохраняет исходные title, description и canonical; его `WebSite` JSON-LD также формируется в React.
- На страницах блога и статьи добавлены `Blog` и `BlogPosting` JSON-LD только из реальных данных. Автор в схеме статьи — автор публикации, Publisher не указан как автор.
- Страницы 2+ блога имеют ссылочные URL `?page=N` и собственный canonical. Список статей можно пройти по ссылкам навигации.

## Состояние до серверной выдачи

Текущий production Nginx для `/` и всех `/blog/...` отдаёт общий `index.html` с пустым `#root`. HTML лендинга и статьи, уникальные метаданные публичных страниц и JSON-LD появляются только после JavaScript и ответа API для блога/статьи. Робот, который не выполняет JavaScript, не получает содержимое лендинга и публикаций. Sitemap помогает найти URL, но не устраняет эту проблему. Это существующее ограничение архитектуры, редизайн его не создавал.

## Реализованное решение (ожидает развёртывания)

С согласия владельца добавлена серверная HTML-выдача `/`, `/blog/:workspaceSlug` и `/blog/:workspaceSlug/p/:postSlug`. Production Nginx проксирует только эти маршруты на backend; кабинет и API сохраняют прежнюю схему. Backend использует `PublicPostService`, который выбирает статьи только со статусом `PUBLISHED` и видимостью `PUBLIC`. Первый ответ содержит основной текст, title, description, canonical, Open Graph, Twitter Card и JSON-LD; отсутствующая или непубличная статья получает 404 и `noindex`. Для нового HTML-ответа и данных первого рендера пользовательская HTML-разметка очищается от исполняемых элементов; исходная запись и существующий JSON API не меняются. React получает данные первого рендера без промежуточного экрана загрузки.

CSS и JS имеют стабильные URL `/assets/app.css` и `/assets/app.js` с `no-cache`. Остальные ресурсы сохраняют версии с хешами и долгий срок кеширования. При временной недоступности API Nginx возвращает прежний SPA `index.html` как резервный вариант; такой ответ не заменяет нормальную SEO-выдачу.

Для остальных SPA-маршрутов Nginx выставляет `X-Robots-Tag: noindex, nofollow`, включая кабинет и страницы входа. Резервный SPA-ответ при недоступности API также получает этот заголовок.

## Остаточные проверки

- Проверить ответы production после отдельного разрешения на развёртывание: HTML без JavaScript, robots, sitemap, canonical, OG, 404 и фактическую доступность статей поисковикам.
- Проверить длинные авторские Markdown-материалы, таблицы, код и медиа на устройствах от 320 px в авторизованной или тестовой среде с реальными публикациями.
- Проверить материалы с ручным HTML: серверная версия сохраняет текст, обычное форматирование, изображения и HTTPS-встраивания, но удаляет исполняемые элементы и небезопасные атрибуты. Исходный материал и существующий JSON API не меняются; после загрузки React может показывать дополнительные авторские HTML-атрибуты.
- Авторский Markdown может содержать `#` внутри тела; тогда на странице будет второй `h1`. Смена уровней заголовков влияет на представление пользовательского текста и требует отдельного решения.
